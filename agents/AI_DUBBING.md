## Performance micro-expression
Describe breath, hesitation, emotional tags, intensity, timbre, pitch contour, articulation, silence and speaker intent. Follow current ElevenLabs model/endpoint tag syntax only after verifying what is actually supported. Inline direction is not proof of a generated vocal performance.

#### Tone and vocal micro-expression compiler

Read `references/fast-performance.md` only for nuanced performance design, cue-pattern lookup or conflicting direction. Routine lines use the compact rules here.

1. Separate **emotion** (what is felt), **tone/subtext** (how it addresses someone), **volume**, **pitch/resonance**, **pace**, **breath/texture** and **micro-expression**. Low volume does not require a lower pitch; anger does not require shouting. Keep character identity stable.
2. Map visible micro-expressions to an audible consequence only when supported by context: a smile → warmth in the voice; held-back tears → a slight catch; realization → a brief breath catch; doubt → restrained hesitancy. Do not send `[eyes widen]`, `[eyebrow lifts]`, head movement or facial animation as TTS controls. Keep visible acting in a Director handoff only when requested.
3. Choose the dominant tone plus at most one useful vocal micro-cue at a beat. Prefer `[soft, reassuring voice]` or `[quietly, voice catching with grief]` over per-word instructions. Add a new tag at an actual emotional turn; never insert tags on every word by default.
4. Distinguish **speaking while crying** from an isolated sob, **a smile in the voice** from laughter, **hushed speech** from whispering, and **contained anger** from a scream. Preserve intelligibility and the exact line. Avoid cues that invite added interjections, stammers or words when word-locked.
5. Infer only a restrained default if tone is unspecified. Maintain the prior tone on a narrow revision; ask only if conflicting instructions cannot be resolved without changing the intended performance. Treat combinations such as fast+quiet or angry+restrained as valid.
6. Compile the internal performance plan into short English natural-language tags and approved dialogue. Do not print the internal axes, profile IDs or QC. Presets in `assets/performance-cues.json` are proposed directions, not tested model commands.

#### Fast line mode: strict contract

1. Output only dialogue with square-bracketed English delivery/emotion tags. Omit heading, character label, explanation, alternatives and code fence unless requested. Do not put character names in tags.
2. Preserve words, repetitions and word order. Add no appeal, sentence, shouted syllable or exclamation word. Punctuation can guide delivery. Preserve an explicitly approved Devanagari line exactly except tags and permitted punctuation.
3. Transliterate Roman Hindi/Haryanvi into Devanagari. Make only requested regional corrections. Do not upgrade simple words into literary synonyms: never automatically change माँ → मैया, साँस → श्वास or बेटा → पुत्र. Keep clause order during authorized adaptation.
4. Start with one concise cue; add another only at a meaningful shift. Distinguish soft sobbing, uncontrolled crying and desperate shouting. “Fast” need not mean “loud”; “crying” need not mean “slow”. Follow the latest emotion/speed revision.
5. Treat tags as probabilistic natural-language directions, not fixed validated commands. Use vocal descriptions; omit environmental SFX from clean dialogue by default.
6. For v4, use supported Stability/Similarity controls; the UI also documents an additional Clone Strength slider specifically for v4 Professional Voice Clones. Do not infer an API field or change an approved setting from that UI control. Do not recommend v4 Speed/Style sliders or SSML break tags. Keep pronunciation experiments separate from locked script.

Example for approved “फेर आँख क्यूँ ना खोल रह्या मेरा पुत्र”:

[crying softly, low trembling voice] फेर आँख क्यूँ ना खोल रह्या... मेरा पुत्र?

Do not move “मेरा पुत्र” earlier or append another plea.

#### 1. Automatic routing

Default to a direct line pass for a short dialogue or performance revision. Reuse active context and the latest exact line; avoid re-reading the playbook or searching official docs for a changed emotion. This is an automatic task-routing policy, not a background automation or a promise to change model inference speed.

Use batch processing when several cues share a cast/language. Resolve shared profiles once, then evaluate cue-specific changes. Do not flatten every cue into the same emotional template. Use the production path only when actual assets, new casting, regional acceptance, API capabilities or audio issues require it.

Maintain only useful context: project/character, approved line, language/variety, voice/model when known, baseline tone, pace, intensity, breath, last explicit override and word lock. Do not invent a persistent cache, a voice ID or a previous line if unavailable. Ask for the missing line only when context cannot recover it.

#### 2. Tone axes and revision handling

| Axis | Examples | Preserve independently |
|---|---|---|
| Emotion | grief, relief, fear, delight, anger | The feeling can be hidden or restrained. |
| Tone/subtext | pleading, reassuring, accusatory, reverent, teasing | Intent toward listener, not merely pitch. |
| Volume | quiet, conversational, projected, shouted | Quiet anger and loud joy are valid. |
| Pitch/resonance | natural, lower register, light resonance | Do not recast a character for one line. |
| Pace | deliberate, flowing, hurried | Fast delivery need not be loud or comic. |
| Breath/texture | steady, breathless, fragile, gently trembling | Keep consonants intelligible. |
| Micro-expression | caught breath, slight voice catch, audible smile | Use sparingly at a meaningful beat. |

For an unqualified “low tone” in Manik's grief scenes, default to quiet, restrained delivery in the existing voice; do not automatically lower pitch. If pitch is explicitly requested, address it separately and audition identity.

Revision examples:

- “thoda fast”: keep current feeling, volume, words and dialect; shorten hesitations and change pacing direction.
- “rote hue”: keep wording and character; change vocal affect without appending sob syllables.
- “zone out hata do”: remove detachment, keep independently requested crying.
- “soft but angry”: use contained firmness; no contradiction needing clarification.
- “smile ho par hasi nahi”: direct a smile in the voice; omit laugh events.
- “chillate hue”: project/shout while retaining the character's motivation; do not add stretched written syllables to a locked name.

#### 3. Micro-expression to voice mapping

These are authored cue hypotheses. They express audible direction, not facial-animation controls and not guaranteed features. A visual detail alone does not require an audible event.

| Contextual beat | Possible audible direction | Avoid |
|---|---|---|
| Tiny relieved smile | `[softly, relief warming the voice]` | Automatic laugh or giggle. |
| Holding back tears | `[quietly, voice catching with grief]` | Sobbing so much the line vanishes. |
| Speaking through tears | `[tearful, gently trembling voice]` | An inserted “हाय” or new appeal. |
| Sudden realization | `[startled, brief catch in the voice]` | Written gasp syllables added to dialogue. |
| Gathering courage | `[hesitant, then quietly firm]` | Random repetitions or stammering. |
| Fear concealed by authority | `[controlled voice, fear underneath]` | Switching to a villain persona. |
| Anger under restraint | `[low intensity, tightly controlled anger]` | Teeth-grinding or aggressive SFX. |
| Affectionate teasing | `[warm, lightly teasing voice]` | Adult sarcasm for a child character. |
| Hurt concealed by politeness | `[polite, voice faintly strained]` | Rewriting the line to explain hurt. |
| Reverent wonder | `[hushed, quietly awed]` | An automatic whisper or chant. |

Remove visual-only cues such as eyebrow raise, eye flick, blink, jaw movement or head tilt from TTS text. If the user requests storyboard/performance alignment, provide a separate optional Director handoff outside a tags-only line request.

Compile no more than the useful audible detail. A short line often needs only one bracketed cue. An emotional turn can justify a second cue. For a long passage, add cues at meaningful changes, not a rigid total cap. Avoid competing directions on the same words.

#### 4. Character performance patterns

Reuse approved character identity before these optional patterns:

- **Anjana:** maternal warmth under distress; grief may produce a small voice catch and pleading softness. A louder cry requires explicit context or request.
- **Kesari:** grounded paternal voice; crying can weaken steadiness without making him detached. Do not keep a removed “zoned out” direction.
- **Vayu:** recognizable parental concern inside authority; urgent rescue calls and controlled wrath are different delivery states.
- **Narrator:** clear story rhythm; a restrained transition can carry more suspense than a tag on every word.
- **Naina:** sincere age-appropriate phrasing; wonder or fear need not become baby talk.
- **Bal Krishna:** warmth and playful composure; direct a slight smile in the voice rather than constant giggling.

Character presets are suggestions until actual casting/scene approval. Never override explicit user tone, dialect, speaker or volume with a preset.

#### 5. Quality and evidence

Before output, run one silent check: exact words/order; correct language; latest override; tone/identity consistency; sparse vocal-only tags; no extra writing. A source/script change invalidates old rendering text. A delivery-only change does not require new source research.

For a delivery-only scene revision, retain its supplied speaker identity and approved Director locks: camera, seated/standing state, supported props and offscreen presence. Keep any visual-reference tag separate from its supplied speaker tag in a production handoff; tags are not dialogue or TTS controls. Revise only audible intent and do not silently restage the scene. This does not add labels or handoff prose to strict fast-line output.

For real audio, also inspect added breaths/interjections, spoken tags, drift, clarity and timing. A text-only check cannot establish these. If a cue adds unwanted reactions, simplify the tag first; do not rewrite approved dialogue to accommodate the artifact.

#### 4. Regional techniques

The techniques here are **recommendations/hypotheses**, not guaranteed vendor features.

##### Three text layers

Keep immutable source dialogue, approved localized dialogue and TTS rendering text separate. Store a change map for spelling aliases or phonetic renderings. Subtitles use approved words without delivery tags. A word-locked cue must preserve every spoken token in order.

##### Native script first, then a controlled comparison

Audition the language's normal script first. If a word fails, compare an approved Roman rendering or alternative target-script spelling. Mixed Roman spellings can cause unintended language switching. A winning rendering is specific to the voice/model, not a universal spelling rule.

##### Grammar before accent

A regional tag cannot fix standard-Hindi grammar. Give the adapter relationships, era, intent and regional variety. Build a phrase bank from the project's accepted lines, recording speaker and situation. Avoid stuffing every sentence with stereotypical regional particles.

##### Native guide performance

A local actor's short reading can establish rhythm, phrase grouping and emotion. Try authorized Voice Changer only within verified support. Hindi STS applied to Haryanvi/Bhojpuri/Rajasthani remains an uncertain experiment, not documented support. Retaining the native actor's recording is a valid quality fallback.

##### One-variable auditions

Compare identical lines with one change: script representation, cue, voice variant or a permitted language override. Changing voice, wording and settings together prevents diagnosis. Have a native listener compare the results without candidate labels where feasible.

##### Pronunciation islands and pickups

Create approved recordings for names such as Hanuman, Anjana, Kesari, Vayu, Narad, Brahma, Vajra and Naina. Keep the proper name stable unless an accepted local convention differs. Repair a word or phrase at a clean edit boundary rather than destroying an otherwise good emotional paragraph. Match intensity and room tone.

##### Code switching

Record intended language and meaning for switched words. A whole-request language override can harm another part of a mixed line; compare with and without it only where the endpoint supports the option. Do not translate names or invocations automatically.

##### Breath and regional rhythm

Get a native reader's phrase divisions. Preserve meaningful repetition such as “देखो... देखो...”. Generate in breath/performance units with adjacent context, avoiding random sentence splits. Authentic rhythm matters as much as individual phonemes.

##### Avoid caricature

“Strong accent” is not a quality target. Check whether native listeners believe the character belongs to the intended region and social register. A non-speaker's preference cannot certify dialect accuracy.

#### 8. Timing and sync

#### 1. Scope and evidence

Apply this reference to episode work and workflow audits, not routine line corrections. Use real project assets and actual approved voice mappings when available. Never fabricate an audio take, native review, source quotation, generation result, connector, measured speedup or saved project record.

Separate three outputs: a prepared prompt/script, generated candidate audio, and an approved delivered master. A well-formed script is not a completed dub. Offline metadata checks do not listen to pronunciation, acting or facial sync.

#### 2. Intake and handoffs

Read only missing information that changes execution. Obtain project and source version, picture version or timing source, locked source words, target language/variety, speaker map, approved casting, desired deliverables and existing assets. Do not interrogate the user about context already supplied.

| Owner / input | Handoff fields | Rule |
|---|---|---|
| AI Writer | Exact source/localized words, intent, relationships, register, allowed adaptation | Do not silently rewrite to fit timing. |
| AI Native Director | Cue/shot IDs, picture segment version, visible mouth priority, breath/action cues, permitted editorial flexibility | Visual acting remains separate from TTS directions. |
| Ai Dubbing | Real voice map, pronunciation version, rendering text, tone arc, selected take, pickup reason | Preserve source words and character identity. |
| Native reviewer | Region/grammar/address/name assessment on actual take, reviewer and evidence reference | Do not substitute ASR for language judgment. |
| Editor / mixer | Accepted audio/stems, cue timing, picture version, subtitle text, delivery specification | Retain original-resolution picture and explicit unresolved items. |

Use current project profiles/shared files when they exist; otherwise use a minimal manifest. Do not claim the other agents were updated or contacted merely because a handoff format exists. Keep shot-local visible character/prop/location bindings separate from audio source and speaker cues. A visual prompt uses only its current on-frame bindings, with no stale cast/props from the scene registry or previous shot. When checking a picture handoff, reject unrelated visual bindings without changing the approved speech cue. #### 3. States and review records

Use these conceptual stages without adding a permission request at every transition:

`draft → source_locked → localized → pilot_checked → generated → reviewed → mixed → delivered`

Record `blocked` with a concrete reason, and `needs_pickup` with cue IDs and failure type. Existing user authorization permits ordinary reversible preparation and repairs. Ask only for a missing decision that cannot be inferred or for an action outside scope. Keep new writing separate when the line is locked.

Store five independent reviews on the selected audio: text, native language, acting, picture sync and technical audio. Each approved review needs a reviewer, evidence reference and the current cue fingerprint. All can be provided by one qualified reviewer if actually performed; never manufacture five approvals from one unchecked status flag.

Keep source/version records and take selection stable. `scripts/cue_qc.py` prints fingerprints but never grants approval. A changed word, tag, model, voice, setting, pronunciation version, cue timing, selected audio hash or relevant picture segment invalidates old review fingerprints. #### 4. Revision handling and pickups

| Change | Minimum affected work |
|---|---|
| Pace/tone/micro-expression only | New rendering for that cue, candidate audio when authorized, then affected review. Keep words and region. |
| Correct a localized word | That language/cue and any generation that actually used it as neighboring context. |
| Character voice change | That character's affected language/version and its continuity benchmark. |
| Pronunciation lexicon change | Cues using the entry; retain prior accepted take until replacement passes. |
| Picture edit | Relevant segment timing/mouth-sync review; do not regenerate unchanged audio automatically. |
| Model upgrade | Pilot/regression comparison first; no whole-series migration by default. |
| Selected take bytes change | New file hash and review; never retain old approval on different audio. |

#### 5. Generation recovery and cost

Use one approved baseline plus a small number of targeted alternatives. Default to at most two new candidate attempts for a failed cue in a repair cycle unless an approved project budget says otherwise. If both fail, diagnose or change route instead of an endless retry loop. Count paid attempts and record actual cost only when returned/measured.

Classify failures before retry:

- Wrong words/pronunciation: fix the rendering/lexicon within word locks; review it before another generation.
- Wrong affect or unwanted reaction: simplify/adjust one cue axis; do not change words to hide the problem.
- Wrong identity: restore voice/model/casting mapping and compare anchor take.
- Timing overflow: preserve intention; try delivery repair before authorized compression or picture adjustment.
- Provider transport error: inspect actual job/request status before resubmitting; ambiguous timeout may still have incurred a charge.
