## Purpose
Create filmable, spatially coherent locations and connected environment/prop reference libraries for AI scene production. Distinguish reference photos, image prompts, floor plans and truly tested 3D geometry.

## Workflow
1. Read story context and visible references; identify period, geography, story needs and fixed landmarks.
2. Research setting details if material. Create preliminary zone map and camera direction map.
3. Present master location plan and establish approval before treating it as canon.
4. Build one master view; derive front/back/left/right, top/ground, inward/outward reverse coverage while preserving doorways, roads, stairs, wall placement and light orientation.
5. For adjacent locations, define physical connectors and permitted walking routes with landmark anchors.
6. Create props with four-view turnaround and photorealistic neutral-grey studio reference photographs when requested; preserve material, dimensions and unique wear marks.
7. Validate back-projected geometry, subject scale, shadow continuity and reference-to-tag mapping.

For a single combined image set `delivery_layout: combined-sheet` and unique `cell_id` per view; its views may share the one sheet output ID.

Use `sheet_status: identified` before coverage is registered, `planned` after allocating all four output IDs, `draft` while images are being checked, and `approved` only after all four are accepted. Record each output's `prop_id`, `prop_version`, file path, actual pixels, status and applicable global versions. Add all four to `required_output_ids` when the set is requested. Tags can bind the prop ID or its existing geometric object ID; preserve their exact strings.

Store studio pose records inside the prop's view records with an explicit object-relative coordinate namespace. Keep world camera/placement records separate; never make the grey photo studio a fictional scene sublocation. Optional detail outputs have their own IDs and do not enter the four-view primary mapping.

Run the manifest validator for IDs, required angles, shared version and output binding. These checks do not certify photographed geometry, grey colour, view direction or readable detail. Inspect those visually.

#### Prop QC and handoff

Check all four photos together:

- Same silhouette/proportion, thickness, components, materials and selected state.
- Real front/rear/left/right orientation; no mirror shortcuts or duplicate-angle substitution.
- Consistent grey background, photographic lighting/exposure, scale and framing.
- Intact complete object, readable texture/important markings and no extra items.
- Correct visible/occluded asymmetric features; continuous wear and material boundaries.
- Exact asset/tag/version agreement with the prop inside its location.

Repair failed views selectively; a shared design change may require updating all four. Record image QA separately from structural validation. Hand the director the approved prop ID/tag, chosen state, view files, dimensions/scale evidence, grip/contact points and placement constraints. Retain learned prop-specific mistakes at their justified scope.

### Continuity QC and repairs

#### Evidence and status

Keep source/tag QC, manifest structure, 3D layout, final appearance, delivered pixels and viewer testing separate. PASS requires an executed relevant check with evidence. FAIL identifies an observed mismatch. PENDING identifies an unexecuted or unresolved check. N/A needs a scope reason. Tool success, a prompt description or a prior assistant statement is not a PASS.

The structural validator checks the manifest contract and references. It cannot determine whether a photograph matches geometry, whether a path is clear, whether a reconstructed wall is accurate, or whether a viewer works. Run those checks separately.

Populate `required_output_ids` with the authorized deliverables at coverage planning. Keep camera/anchor outputs in `outputs` even when planned, so a missing requested artifact cannot disappear from the completion count. For each executed QC record set `id`, `category`, `status`, `evidence`, `required` and `output_id` when applicable. An approved final image needs relevant tag, geometry/appearance and file checks; a requested interactive panorama also needs executed viewer QC. Do not reduce these checks to one generic PASS.

#### Checks by stage

| Stage | Inspect | Failure examples |
|---|---|---|
| Master | Script requirements, visible architecture, count, route, reference identity | Wrong regional vegetation, extra idol, blocked walkway |
| Blockout | Matching master camera, building silhouette, scale, coordinates, openings | Added window, wrong depth, staircase going wrong way |
| Connections | Both sides of shared opening/steps, elevations, adjoining environment | Door leads to unrelated room, discontinuous landing |
| Camera render | Pose, lens/sensor convention, occlusion, foreground/background | Camera inside wall, false top-down, accidental mirrored view |
| Final image | Compare to exact camera render and appearance master | Moved neem, enlarged charpai, vanished well, extra door |
| Prop photos | Four true sides, neutral grey, identical asset/state, scale and detail | Mirrored side, duplicate angle, different strap/hardware, cropped tip |
| Angle set | Opposing and neighboring views, shared landmarks and material identity | Correct-looking singles that disagree as a set |
| Scene route | Start/end surfaces, passage, contact heights, actor scale | Invisible support, blocked exit, child/adult scale change |
| Panorama | Anchor placement, projection, wrap, poles, actual world surroundings | Sky stripe, floor pinching, duplicated house, changed village |
| Viewer | Actual image loads; drag/zoom and full rotation work; narrow width | Flat bitmap, inverted look direction, blank canvas, seam at wrap |
| Delivery | Files decode, dimensions, names, versions, durable save | Truncated PNG, incorrect 4K claim, stale output in approved set |

Use overlays with aligned camera references where possible. Compare landmark positions, silhouettes and occlusion rather than expecting all textured pixels to match a gray blockout. Inspect significant texture/detail locks against the approved appearance reference. Keep any numerical alignment metrics tied to an actual recorded method.

#### Critical failures

Do not deliver an approved pack with any of these unresolved:

- Unauthorized master/reference/tag change.
- Missing required zone or scene route.
- Changed opening/step/object count or a shared boundary that does not connect.
- Camera-dependent world mirroring, misplaced key anchor or impossible floor level.
- Different surroundings in a connected reverse view.
- “Seamless” claimed without wrap/pole checks, or “interactive” claimed without a working viewer.
- Essential camera/frame mismatch hidden by blur, crowd or crop.
- Corrupt deliverable or unsupported resolution/save claim.

Minor texture differences still need a specific note when they remain. Promote them to critical if they affect hero detail shots, story clues or matching landmarks. Do not invent an allowed percentage of drift.

#### Repair loop

1. Record output/view/version, failed criterion, visible evidence and dependencies.
2. Determine whether the cause is geometry, camera, scene state, material, asset/tag binding or generative drift.
3. Repair the actual cause. A wrong camera render needs a camera fix; an accurate render followed by a shifted door needs a final-image repair.
4. Preserve approved architecture and stable IDs. Change the design only if the user authorizes that change or it falls within delegated unapproved design scope.
5. Regenerate the smallest affected set; do not launch dependent generations from a failed image.
6. Inspect the repair plus its relevant opposing/adjacent view and boundary.
7. Mark accepted, superseded and stale files explicitly. Update status and save.

Avoid repeated identical requests when the same error persists. Diagnose the constraint, reduce competing prompt detail, supply a tighter supported reference or switch to a supported direct render. If still limited, report exactly which property remains unverified without overstating completion.

#### Panorama inspection procedure

Inspect a horizontal wrap by showing the original edge join in the middle of an offset inspection image where supported. Test a perspective view through that join, zoomed enough to reveal geometry and exposure discontinuities. Look straight up/down to check pole artifacts. Look back to the approved house/temple landmarks to ensure the repair did not change the world.

Run a full 360-degree drag/turn cycle, vertical look and zoom in the actual viewer. Verify correct initial landmark orientation and narrow mobile layout. Save the test result or screenshot/trace path. If runtime inspection is unavailable, record PENDING instead of inferring success from static code.

Use image-generation tooling for generative repairs according to its rules. Format conversion, texture offset and projection inspection do not justify replacing the approved environment. Keep diagnostic files distinct from final output.

#### Completion report

State the smallest useful result: accepted master/version, requested versus delivered views/zones, actual 3D versus schematic status, requested panorama/interaction test status, significant pending items and direct deliverable access. Do not bury a critical failure under “all complete.”

### Shared spatial contract

#### Contents

- World coordinates and evidence
- Objects, appearance and scene state
- Connected zones and openings
- Coverage boundary and movement
- Cameras
- Panorama anchors

#### World coordinates and evidence

Use metres and a right-handed world: +X east, +Y north, +Z up, unless the existing project already uses a documented convention. Put origin on the ground in a useful central open area. Keep the origin stable after lock; a panorama anchor is a camera location, not a new origin. Record whether compass orientation is geographic evidence or a design convention.

Store all object and camera positions in world coordinates. If the modeling application uses local transforms, resolve them to this world before export. Keep parent relationships for ownership without assuming a second coordinate convention. Never mix local and world positions silently.

For each significant asset record dimensions, pivot convention, rotation, material reference, source, design status and exact asset/tag. Treat measured, estimated, proposed and approved scale differently. A single photograph often cannot establish depth or hidden faces uniquely. Maintain uncertainty until the layout is adopted as a production design.

#### Objects, appearance and scene state

Give each physical object a stable unique ID: wall, opening, threshold, steps, roof, window, neem, charpai, well, railing or altar. Do not add duplicate geometry because an asset belongs to two zones. Reuse one material and shape definition across all cameras.

Define real openings in the walls when a camera or actor must pass or see through them. Door surface, doorframe and wall opening are related but different physical components. Give the assembly a shared ID that both sides use. Model thickness, sill/threshold level and swing where relevant. State whether a door is closed/open per scene preset.

For stairs record start/end elevations, riser/tread count and dimensions, run direction and landings. Separate temple gate steps from shrine steps. Check that the ascent/descent direction in a reverse is derived from geometry, not the word “reverse.” For overheads, use a camera looking straight down; label oblique overview separately.

For appearance, lock large material regions and distinctive landmarks before small decorative texture: exposed brick patch, broken parapet corner, door crossbar, one shuttered window, canopy/trunk shape. When closeups matter, use explicit detail assets. A coarse blockout cannot determine every carving or crack; do not label detail matching as verified unless inspected against its reference.

Keep two state layers: persistent architecture/assets and scene-specific changes. Encode lighting, door angle, moved prop and crowd configuration in a state preset. Do not bake an actor into the empty location master or force a furniture position to remain fixed when a scene explicitly moves it.

#### Connected zones and openings

Represent sublocations as regions within the shared scene with stable zone IDs, memberships and parents. Distinguish:

- **Same-place views:** different cameras seeing one area.
- **Attached sublocations:** rooms, stairs, courtyard and lanes joined physically.
- **Separate story locations:** do not assign shared geometry without evidence.

Every physical connection records the two zone IDs, one shared boundary/opening object, and endpoints in the same world coordinates. For a doorway endpoint pair, the points must coincide within the documented assembly tolerance; floor/step transitions remain explicitly modeled. A corridor or stair route can have different endpoints connected by a path, not a false coincident-doorway assertion.

Save opening width/height, boundary orientation, floor elevations and transition type. Keep both sides' materials, scale and visibility consistent. A shrine's interior doorway must map to the same entrance seen from the courtyard. Door and portal centrelines are useful QC landmarks.

Use records like these as shapes, not project facts; replace example IDs and values from the approved layout:

```json
{
  "object": {"id": "shared-entry", "position_m": [0, 0, 0], "dimensions_m": [1.2, 0.25, 2.1], "rotation_deg": [0, 0, 0], "pivot": "bottom-centre", "parent_id": null, "design_status": "proposed", "material_ref": "approved-door-detail"},
  "zone": {"id": "room", "parent_id": null, "object_ids": ["shared-entry"]},
  "connection": {"id": "yard-room", "type": "opening", "from_zone": "yard", "to_zone": "room", "shared_object_id": "shared-entry", "from_point_m": [0, 0, 0], "to_point_m": [0, 0, 0], "tolerance_m": 0.01}
}
```

Add a route record with `id`, `points_m` and its actual clearance/contact evidence. Record external image files separately from geometric dimensions. Dimensions of a bounding box do not replace an opening mesh or a collision check.

#### Coverage boundary and movement

Use a finite boundary around required camera/actor paths plus visible foreground, background and adjoining areas. Model near occluders and geometry in shot sightlines. Include enough side/rear geometry for planned diagonals, reverse angles and height changes. Avoid an infinitely large set when only one house and adjacent streets are required.

Record important movement paths as world points plus start/end zones, clearances and contact surfaces. Check passage around furniture, through openings, across thresholds and up/down steps. Use actor scale references and required crowd width from the brief; do not invent numerical clearance standards as universal facts.

Track moving props and background extras separately from permanent anchors. At a blocking handoff, give the director a supported path, floor levels and occlusion opportunities, not a vague direction such as “towards the temple.”

#### Cameras

For each reference view record:

- Stable camera/view ID, zone, explicit purpose and exact existing tag if any.
- Projection: perspective, orthographic or equirectangular.
- World position and target, documented up vector/roll, clipping.
- Lens focal length, sensor width and sensor fit for perspective; ortho scale for orthographic.
- Aspect ratio and requested/actual output pixels.
- Light and scene-state preset; visible and intentionally occluded asset IDs.
- Geometry/material/master version, render path and downstream dependencies.

Store target-based pose or a documented orientation representation consistently. With the adopted convention, top-down uses target below the camera; use an appropriate horizontal up vector, avoiding collinearity. A viewpoint name is not its orientation: derive screen-left/right from the actual camera. An actor's action axis is a separate editorial constraint supplied by AI Native Director.

When importing reconstruction/research camera poses, record source pose direction, quaternion order, camera axes, source units and source-world-to-project alignment before using them. For the documented COLMAP `images.txt` image pose only, `(qw,qx,qy,qz)` is a Hamilton world-to-camera rotation and `t` is not camera position: derive `C=-R^T t`. Camera-local axes are right/down/forward; derive visual up from negative camera Y, then apply a documented world-alignment transform to centres, directions and geometry consistently. Do not assume SfM coordinates are geographic or metre-scaled, guess `xyzw`, or reuse this rule for unresolved rig/body or camera-to-world poses. Keep missing alignment/scale/landmark verification pending; never move approved architecture to accommodate an import error. The optional read-only helper in `production-runtime.md` checks arithmetic only. Source: [COLMAP output format](https://colmap.github.io/format.html#images-txt), baseline documentation checked 2026-10-20, not a new release or measured quality improvement.

For manifest perspective cameras use `id`, `zone_id`, `position_m`, `target_m`, `up`, `projection`, `lens_mm`, `sensor_width_mm`, `sensor_fit`, `aspect`, `light_id`, `state_id` and `visible_object_ids`. For an anchor use `id`, `zone_id`, `position_m`, `zero_heading_deg` and optional `panorama_output_id`. For outputs use `id`, `status`, `path`, camera/anchor ID, `pixels`, geometry/material/state versions and `depends_on_output_ids`. Keep `planned` outputs before generation; advance only after inspection.

Pick lenses for a readable location reference, not shallow-focus actor portrait style. Keep geometry QC references sharp enough to see anchors. Save cinematic focus/blur as a separate shot choice so it cannot hide missing or incorrect geometry.

For calibrated pinhole references, bind pixel intrinsics `K` to the exact source resolution and preprocessing record. Resize/crop/padding changes pixel coordinates, not world geometry: record the actual source-to-output pixel map `A` and derive `K_output = A K_source`. For crop-then-scale with origin-scaled coordinates, `fx'=sx*fx`, `fy'=sy*fy`, `cx'=sx*(cx-left)+pad_x`, `cy'=sy*(cy-top)+pad_y`; other resamplers can require pixel-centre offsets. Do not guess the convention or reuse stale intrinsics merely because lens/pose or output dimensions match. Preserve the original and its approval; version the processed derivative. Keep alignment pending when preprocessing/calibration is unknown. Do not apply this pinhole rule to equirectangular, fisheye, undistortion or generative reframing; those require their own mapping/model. See the read-only helper in `production-runtime.md`. This is a mathematical consequence of the [OpenCV 4.13.0 pinhole projection and resize documentation](https://docs.opencv.org/4.13.0/d9/d0c/group__calib3d.html), checked 2026-10-17; it is baseline documentation, not a new release or measured image-quality gain.

#### Panorama anchors

Place anchors in useful accessible positions at documented eye height: courtyard centre, charpai side, gate landing or sanctum. Keep them away from geometry intersections. Each anchor records position, zero-heading/longitude orientation, camera height, world version, state/light preset and render provenance.

Render full-sphere equirectangular textures with 360° horizontal and 180° vertical coverage and a 2:1 canvas. Other panoramic formats need their own explicit projection. Set orientation for a recognizable landmark and maintain it across viewers. Do not stretch a normal wide-angle photo and call it equirectangular.

Treat a panorama as a rotational view at a fixed point. Changing anchor requires a separately rendered view. Reprojecting or cropping a single panorama does not recreate translated viewpoints or hidden surfaces. A clickable tour moves between anchors, while an actual 3D viewer can move cameras through the geometry; label the mode accurately.

Prefer anchors from the shared scene. AI-only panorama drafts need separate layout, wrap and pole verification. Assess image resolution by actual visible detail after viewport projection, not the width number alone.

For an interactive viewer, include the actual texture and working touch/drag plus zoom. Verify initial heading, up/down orientation, full wrap and layout on narrow screens. Test the seam in perspective, not only as a flat image. A seamless join cannot validate that all surroundings match the master.

#### Changes and tolerances

Before comparing renders, document useful tolerances for that set and camera: anchor position, silhouette, door/step count, actor scale and image alignment. Define numeric image tolerances only when the camera is calibrated and the method is actually computed. Do not invent a similarity percentage from visual inspection.

Keep stable object IDs while increasing geometry/material/state versions. Record who authorized the change and its scope. Determine affected outputs through visibility, connection and dependency records. Mark those stale; regenerate required views and anchors, then inspect the corresponding opposing/boundary views. Preserve unaffected approved files.

### Staged location workflow

#### Contents

- Approval and resumption
- Source-to-location map
- Master image and questions

#### Approval and resumption

Record state transitions in the manifest:

`brief_ready -> master_draft -> master_review -> master_locked -> layout_questions -> layout_ready -> blockout_ready -> camera_references -> final_views -> qc -> delivered`

This is the `master-first` path. In `researched-agent` mode prepend `context_ready -> research_ready -> plan_review -> plan_locked` between `brief_ready` and `master_draft`. Use the controller reference for versioned plan/master approvals and worker coordination. An approval request concerns the concrete plan or image already presented; a routine research action needs no extra gate.

Allow branches `revision_requested` and `capability_limited`; store the last completed stage and next required action. A generated master is a draft until user acceptance or explicit delegated design authority. Approval of the master authorizes preserving its visible design; it does not prove unseen construction or scale. Carry existing authorizations forward.

If the user says “good, ab saare angles banao,” bind the accepted image/version, check any already answered layout questions and continue within that instruction. If the user says “pehle sirf ek image,” stop after producing and checking that one image. If the user asks only for prompts, provide prompts without generating assets. If the user explicitly changes the flow, honor that change and record it.

For “resume,” read state and existing outputs; inspect files that remain available, recover important sources through supported access and complete the missing stage. Do not restart, regenerate all views or mark completion from an earlier assistant statement alone.

#### Source-to-location map

Create a compact working table:

| Scene/beat | Required zone | Interaction/route | Must-visible anchors | Adjacent geography | Evidence |
|---|---|---|---|---|---|
| Supplied scene | Named or proposed zone | Who moves where; support/contact surface | Doors, steps, furniture, trees | Start/end location and connection | Script/user/image/proposal |

Cover the scenes that use this location, including entrances and exits. Do not merge similar settings just because their props resemble one another. Keep mutable scene state separate from persistent architecture: an open door, moved stool, crowd or different time of day is a state preset, not a replacement building.

Use script facts to determine design: a couple must rise from a charpai and join a passerby; a blind character needs plausible walking/contact surfaces; a procession needs enough route width; a reveal needs a real occluding wall. Hand character performance to the directing workflow.

#### Master image and questions

Make the master sufficiently wide to read meaningful distances and routes, but do not force an entire complex into one distorted frame. A large temple can use an architectural overview as its master plus connected zone seeds after approval. Keep master composition and architecture distinct: a required camera composition must not be changed merely to make the layout easier.

After master acceptance choose up to two questions with highest downstream impact. Example question pair in Hinglish:

1. “Ghar ke liye exterior aur aangan hi chahiye, ya screenplay mein andar ka kamra bhi cover karna hai?” Recommend the scope supported by the scenes; offer exterior-only or connected interior as appropriate.
2. “Ghar ke saamne aur side lane ka environment existing reference se lock karein, ya same gaon ke hisaab se main design karun?” Recommend existing reference if available; otherwise recommend a restrained consistent design.

Other high-value questions: a route's unresolved destination, a courtyard-to-sanctum opening, the level difference between gate and shrine, shared wall versus separate building, a disputed unseen side or required night/day coverage.

Do not ask “kitne angles?” when scene coverage can determine it, “same colour?” when already approved, “4K?” when already established or “kahan save karun?” when the destination is known. Do not ask questions to fill a quota. Keep the stage to one short batch, with recommended options and their effect on scope.

For optional unanswered choices, proceed with stated defaults and mark unseen design as proposed. For actual conflicting constraints, do not silently choose one; clarify only that conflict. Build independent inventories and camera coverage while waiting.

#### Coverage and capabilities

Define a finite production boundary covering camera sightlines, movement destinations, approach/reverse views and key occluders. “Poora area” means the documented set and its required surroundings, not an infinite world. Near geometry visible in reverse shots needs explicit design; distant background can be an approved backdrop if parallax is irrelevant to planned movement.

Use a capability table internally:

| Capability | Execution | Claim boundary |
|---|---|---|
| Image generation available | Generate/edit with exact available references | Inspect output; tool success is not continuity PASS |
| 3D engine available | Build and render the scene, save editable source | Actual camera geometry; reconstruction may still be provisional |
| No 3D engine | Save coordinate model and code/SVG schematics as supported | Reference-only branch; do not call it camera-verified 3D |
| Conditioning available | Apply supported camera render/depth/edge/mask inputs | Record actual tool input; a prompt cannot substitute for a conditioning channel |
| Viewer supported | Embed actual texture, wire touch/drag/zoom, test | Interactive only after runtime/interaction check |
| Viewer cannot be tested | Deliver supported preview/source and precise pending status | Do not assert verified seamless viewing |

Do not install software, build an external account workflow or change unrelated project content solely because the preferred branch is unavailable. Use the best authorized supported branch, complete independent work and disclose the specific limitation. Obtain critical references when exact matching requires them.

Choose views by need. The reusable exterior set often includes overall, front, reverse, left, right, ground and top-down; the master already supplies overall, so avoid counting it twice. A tiny doorway may only need both sides and a contact detail. A sanctum may need its wall directions, floor and ceiling; define which camera sees which wall. Always honor explicit named views and inherited tags.

Generate front/reverse or the most important opposing pair first. Check shared anchors and boundary before dependent details. Group by zone in the manifest, not by separate disconnected worlds. Record useful scene-specific camera records such as route-tracking start/end or child-height insert, without inventing actors in empty location references.

#### Output pack

Keep only useful production artifacts:

- Approved master with version and verified dimensions.
- Location manifest and source/approval/asset register.
- Editable actual 3D source when built, plus top-down and 3D overview.
- Connected zone map and camera records.
- Camera-specific references, supported guidance maps and requested final images.
- Requested anchor panoramas and interactive viewer with test status.
- QC record, repair dependencies and exact pending items.

Use stable names, e.g. `<location-id>-v01/<zone-id>/<view-id>.png`. Keep superseded outputs outside the approved set. A 3840x2160 image is 16:9; a full-sphere panorama normally needs a 2:1 canvas such as 4096x2048. Do not call a 16:9 resize a full sphere or assert these dimensions if the tool did not return them. Follow actual tool size support; record requested, native and exported dimensions separately.

#### Worked production example

Use the Sharda–Avdhesh home example only as a method example, not universal project facts. In the visible conversation, the approved visible design is a modest old mud-brick/plaster house, window left, wooden door centre-right, one neem and one charpai front-left, clay pot near door, open dusty forecourt and village path/side lane. Scene references must still be verified from the actual supplied script in a new project.

Finalize the master; ask whether an interior is needed and how unseen reverse surroundings should be designed. Set a ground origin in the forecourt. Create the house shell, actual door/window openings, neem, charpai, pot and both lanes with fixed positions. Make the front/reverse, diagonal, low and top-down views come from that model. Attach any needed room through the same doorway. Keep a clear charpai-to-road route.

Choose forecourt, charpai and lane-junction anchors only if useful. Do not invent multiple photoreal panoramas independently and then call them one world. Preserve the approved village surroundings during seam repairs. Save camera positions and reference IDs so the storyboard workflow can use the same geography.
